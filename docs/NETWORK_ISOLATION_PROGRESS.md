# 浏览器环境与网络隔离实施记录（v3 → v4）

首版日期：2026-09-30。最近代码实测：2026-10-08。最近方案修订：2026-10-10。分支：`codex/browser-network-v3`。

**本次交付是独立环境管理和 M1 实验原型，不是完整 v3，也不是已经可用的严格网络保护。** 用户确认没有专用 Windows 测试机/虚拟机；没有在日常主机写入 WFP 策略，没有创建 TUN、改系统代理/路由/DNS，也没有迁移真实账号 Profile。`network.getCapabilities` 固定返回 `available: false / M1_NOT_ACCEPTED`。

**当前决定（2026-10-10）：用户已接受每组独立 Chrome 副本，目标计划更新为 v4。** 本轮仅修订文档，现有配置编译器、共享 `chromePath` 的 WFP 工具和认证实验仍属于 v3；不能被视为新路线的实现或验收。

**最新阻塞证据（2026-10-08）：冷 WSS 未通过。** 无先前代理认证缓存时，WSS 不触发当前 CDP Fetch 认证处理，有头/后台均失败。此前 WSS 通过项发生在页面已完成认证之后，不能据此认定冷状态可用。失败复现、关闭处理和其他回归结果见下文“冷认证门槛与 HTTP 403”。

## 已接入产品的环境管理

- schema 7 追加 `account_environments`；已有和新建账号默认继承，旧 DTO 不新增字段。固定配置保留账号语言、时区、版本；换组/删除组不清除固定值；恢复继承不删除 Profile。
- 环境修改校验语言标签和时区，使用 `expectedVersion` 拒绝冲突。每个浏览器保存不可变启动快照，页面查询显示当前运行值、下次使用值和待生效状态，不改已打开窗口。
- 继承继续使用既有分组手动/自动探测逻辑；缺少语言时保留原应用默认 `zh-CN`，缺少时区时不传覆盖值，由 Chrome 决定。已取得的部分地区值继续保留，探测失败不被永久写成固定配置。查询复用地区推导纯函数，不访问公网；`probePending` 明确标识下次启动仍需探测。
- 修复 broker 后台启动没有应用地区时区的问题。普通继承模式的有头窗口恢复原有时区设置行为，不再因为默认语言存在就安装持续的环境屏障；明确选择账号固定的窗口才在 broker 接管前安装环境屏障。后台保留原身份屏障并应用配置值。不新增 Canvas/WebGL/字体/音频伪造。
- 账号详细配置新增环境面板，可保存固定配置或显式恢复继承。详情每 2 秒查询、失败退避至 30 秒，多卡片串行查询，隐藏到托盘停止业务查询。显示两个既有付款直连域名以及严格保护暂不可用。
- IPC 升至 1.4，新增 `environments.get/update/reset` 与 `network.getCapabilities`。没有注册尚未实现的网络变更/恢复/诊断接口；不返回虚构的 Operation 或“已阻断”。全局事件流及旧错误 envelope 保持不变。
- 升级数据库在 Agent 启动、运行写入开始前 checkpoint 并创建一致性备份；未指定备份目录时使用数据库旁的 `backups`。回退程序需要停机恢复备份，不自动覆盖数据库。

## M1 原型补强（2026-10-08）

`installBrowserStartupBarrier` 将原认证实验与身份/环境初始化合并为一个原始 CDP 连接。Playwright 保留自身控制连接；这不是宣称浏览器只有一个 CDP 客户端。普通模式仍使用原生产启动路径，没有将新屏障接入其中。新增命令时限与 `control_error` 状态：通道仍连接但不再回复命令时通知关闭处理，不把控制失败显示成网络已冻结。

合并中复现了新的 Service Worker 死锁：安装事件等待 fetch 完成，而初始化回执又依赖 Worker 继续运行。只给 Worker 入口脚本放行仍会死锁。最终原型先确认 Fetch 认证拦截和递归附加，再按序排入身份与观察命令，允许 Service Worker 的安装请求完成；文档页面请求继续等待完整回执。该差异有独立回归，不将命令排队等同于已完成。晚到的错误仍使该次运行失败。

Profile 守卫不只检查 `app_bound_encrypted_key`：它遍历所有顶层 Profile 的 `Cookies` 与 `Network/Cookies`，连同 WAL 复制到临时目录后只读查询，遇到 `v20`、未知/异常密文、损坏数据库、非空回滚日志、孤立 WAL、链接目录或检查期间变更就拒绝。原数据库不参与 SQLite 恢复，不读取 Cookie 域名或解密数据进入报告。`eligible` 只表示格式守卫允许进入后续实验，`migrationVerified` 始终为 false；正式切换所需的准入锁尚未实现。

WFP 实验工具通过策略中的完整 Chrome exe 清单生成默认出站阻断，辅助程序不自动得到主程序的放行。实际文件哈希、新增或遗漏 exe 会在运行前校验；本机测试 Chrome 副本共发现 10 个 exe。清理键仅取自保存的策略，因此二进制损坏或丢失后仍可计算原规则键。清单与哈希还不能替代管理员保护目录、来源签名或更新协调器。

端口预检查同时读取 IPv4/IPv6 的实际 TCP 动态范围、排除范围及占用情况，拒绝低端口、交叠和无法识别的查询结果；不会更改系统范围。它是检查快照，尚未解决检查至绑定之间的竞争，也没有实现持久化端口规则的自动回收。

本轮定向测试 25/25 通过，包含 Service Worker 回执依赖、CDP 无响应、WAL 中的 v20、原数据库/WAL/SHM 字节不变及异常格式拒绝。显式开启真实 Chrome 的实验 3/3 通过：有头与后台均验证页面、popup、同源 iframe、dedicated/shared/service Worker 的初始环境和认证，副本路径保留合成登录。脱敏报告为 `auth-3GhHyU/report.json`、`auth-lvKeQS/report.json`、`runtime-BvMXqm/report.json`（均在 `artifacts/network-lab/`）。这仍不覆盖真实账号或 Chrome 版本升级。

NativeAOT 发布、`selftest`、示例结构校验、主机端口只读查询及真实 Chrome/mihomo 副本的 `preflight` 均通过，未执行 WFP 写入。预检查策略保存在 `artifacts/network-lab/runtime-BvMXqm/preflight-policy.json`，上游为不可用的测试保留地址，未启动代理连接。早期死锁失败报告保留供对照。

随后全量 Node 回归 657 项：650 通过、7 跳过、0 失败、0 取消，约 71 秒。报告为 `artifacts/network-lab/m1-prototype-refinement-node.tap`；其中网络实验默认跳过，以上 3 项显式开启的实测单独记录。前端、Rust 与 IPC 代码本轮未改动，未将此前结果标成新的复测。

## HTTPS 与双组认证矩阵（2026-10-08）

新增 `networkAuthMatrix.integration.test.js`，分别以有头和后台模式运行两组真实 Chrome、两个 mihomo 及两条可辨识的本地转发链路。两组访问同一 HTTPS 源站，验证首次 CONNECT 认证、WSS、Cookie/Local Storage 独立、不同语言时区；跨站 iframe 使用两个数值回环站点，开启 `--site-per-process` 后还要确认确实出现 `iframe` 类型的 CDP Target，不能仅以 DOM 中有 iframe 作为覆盖证据。

HTTPS 夹具在全新测试 Profile 的证书库中信任本次临时 CA，不导入 Windows 证书库，不使用忽略证书错误的参数。不可信 CA 和主机名错误分别必须产生对应的 Chrome 证书错误，同时不能被误判成代理认证失败。测试 CA 私钥仅在生成进程内存在，站点私钥在结束时删除。Profile 证书库按 Chromium schema 1 构造，属于版本相关的测试夹具，不是生产证书安装方案。本轮只证明 HTTPS 网页经 HTTP 上游代理的链路，未证明 HTTPS 类型上游节点的 TLS/SNI 兼容。

换组用例暴露并修复了原型中的关闭竞争：直接发送 `Browser.close` 后，正常 CDP 断开触发 `onFailure`，立即终止 Job，可能抢在 Cookie 落盘前结束 Chrome。失败报告 `matrix-2WiCzB/report.json` 保留了 Cookie 丢失复现。新增 `requestBrowserClose()` 保持认证处理并进入 `closing`，正常断开不再触发该强杀；Job 清零仍由调用方独立确认，不能以 CDP 消失代替。未请求关闭的断连仍故障关闭，请求关闭后连接尚在但没有命令回执仍报错。只修正实验原型，未替换普通模式的关闭实现。

错误凭据用例还发现：mihomo 1.19.29 对提交的错误凭据返回 403，而不是再次给出 407。[对应实现](https://github.com/MetaCubeX/mihomo/blob/v1.19.29/listener/http/proxy.go#L141) Chrome 将 CONNECT 的这类失败报告为 `ERR_TUNNEL_CONNECTION_FAILED`，原屏障只等下一次认证挑战，因此没有主动关闭。现在将该错误与本屏障刚提交凭据且尚未完成的请求关联，按认证链路未确认处理并关闭；不把所有隧道或站点证书错误都当成密码错误。`matrix-Qw6ODP`、`matrix-toKbv3`、`matrix-HL1GOZ` 保存了失败对照，报告只记录白名单错误码和计数。

扩展矩阵包括：入口与快照不符时不提供密码；入口匹配但使用另一组凭据时不进入上游；上述失败不影响另一组浏览器；旧 Job 清零后复用测试 Profile 换组，Cookie 保留并重新认证。测试中的手工关闭/换组顺序不等于生产变更协调器已经完成。普通 HTTP 的 403 仍需区分代理认证拒绝与业务站点拒绝，这一项不能从 CONNECT 用例推定通过。

最终显式运行新旧认证实验 4/4 通过，约 95 秒；报告为 `artifacts/network-lab/auth-matrix-complete.tap`。扩展矩阵的有头/后台原始报告分别是 `matrix-xOzB0c/report.json`、`matrix-YA3Pcv/report.json`，原 HTTP/WS/Worker 回归分别是 `auth-CTkvct/report.json`、`auth-W1RDCi/report.json`。每个扩展矩阵有 11 项检查，所有测试浏览器 Job 均确认清零；源站观察到的请求均由本测试代理转发，未收到代理密码。这只是明确测试目标的正反对照，不是主机全流量无泄漏证明。10 项屏障单元测试通过，其中新增主动关闭正常断开、关闭命令卡住和关联 CONNECT 错误的回归。

随后全量 Node 回归 662 项：653 通过、9 跳过、0 失败、0 取消，约 73 秒，结果位于 `artifacts/network-lab/auth-matrix-node-regression.tap`。额外的两个跳过项为默认需要显式开启的新矩阵。本轮没有更改 WFP 工具、前端或 Rust，未重跑对应构建与测试；没有写入系统网络规则或系统证书库，严格模式能力仍不可用。

## 冷认证门槛与 HTTP 403（2026-10-08）

继续扩展矩阵后确认现有方案的实质缺口：全新测试 Profile 从 `about:blank` 第一次连接本地 WSS 时，没有收到 `Fetch.authRequired`，Chrome 只报告 `Network.webSocketFrameError` 的确切文本 `Proxy authentication failed`。另一全新 Profile 先通过 HTTPS 完成认证，再回到 `about:blank` 连接同一 WSS 端点则成功；证书、来源页面和目标保持相同，区别是认证缓存是否已建立。有头和后台均重复复现，不能用页面预热后成功代替冷状态通过。

原型现在将这一确切错误报告为 `control_error` 并通知关闭实例，未请求任何自动重试。测试确认失败实例 Job 清零。这修复了“失败后仍显示 ready”的处理缺口，**没有**解决冷 WSS 认证。验收断言仍要求冷 WSS 成功，因此两项 `M1 cold authentication acceptance gate` 明确失败，不标 todo、不当预期成功；严格模式产品集成继续停止。

同一实验还启动独立全新 Profile，让 blob dedicated Worker 的第一次 HTTPS fetch 成为首个代理业务请求，观察到新的认证挑战且到达正确上游；有头/后台均通过。这不是 shared/service Worker 的冷状态验证，也不代表已经清除了一个运行中 Chrome 的认证缓存。[Chromium 的 CDP 实现](https://chromium.googlesource.com/chromium/src/+/main/content/browser/devtools/protocol/network_handler.cc)中，清网页缓存和清 Cookie 各走不同的数据清理路径，不能把任一调用成功当作代理认证缓存清除证明。本轮使用全新 Profile 证明冷状态。

HTTP 403 则采用独立诊断，不猜测状态码来源。新增 `probeMihomoAuthentication` 对已登记的数值回环入口使用三个新连接，发送没有转发目标的 origin-form `GET /`。对固定 mihomo 版本分别验证无密码的 Basic 407、随机错误密码的 403，以及指定密码后的本地 400；异常响应、免认证、忽略错误密码及超时均为“未确认”，不能通过。真实 mihomo 实验证明正确/错误凭据分支按预期返回，且上游计数不变；正常业务站点的 403 仍交给网页处理。

该诊断不是端口身份鉴定，不识别每个业务响应的来源，也不填充 Chrome 的认证缓存；检查后进程、端口或配置变化仍需协调器和 WFP 约束。当前未接入生产启动。后续可作为已证明进程归属后的启动前检查候选，但不能用它把未知 403 判为网站拒绝、关闭所有返回 403 的页面，或假定冷 WSS 已解决。
